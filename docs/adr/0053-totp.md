# ADR 0053: TOTP as a second factor

Status: Accepted (2026-11-10). Phase 5, work package 5.29 ([plans/phase-5-auth.md](../plans/phase-5-auth.md)).

## Context
VPN and administrative logins increasingly need a second factor. The common one is a time-based code from an
authenticator app (RFC 6238). RADIUS carries it in two ways: the NAS shows an Access-Challenge's Reply-Message and
sends the code with the State (most VPN gateways), or the user types the code after the password (clients that
cannot show a challenge).

## Decision
- A user (or group) with **`TOTP-Secret := <base32>`** needs a code; at least 80 bits. Users without it are unaffected.
- **`auth.totp.mode = challenge`** (default): the password is checked first; if right, an Access-Challenge with a
  fresh 16-byte State and `auth.totp.prompt` asks for the code; the next Access-Request carries the code as its
  User-Password and the State. The State is used once, belongs to the user and expires after `auth.totp.timeout`.
  A wrong password never gets a challenge.
- **`append`**: the last `auth.totp.digits` characters of the password are the code; the rest is checked as the password.
- HMAC-SHA-1, 30-second steps, 6 (or 8) digits, `auth.totp.window` steps of drift either way (default 1). A code is
  accepted **once** per user: a step at or before the last one used is rejected.
- Only PAP: CHAP, MS-CHAP and EAP do not reveal a code; a TOTP user trying them is rejected.
- Reply items, limits, pools and rules apply to the round that accepts.

## Consequences
- Challenges and used steps are kept per gateway: a NAS must send both rounds to the same gateway (as for EAP), and a
  code could be replayed once on another gateway within its window.
- Secrets sit in the store like passwords; enrolment (generating secrets, QR codes) is outside radiusward.
