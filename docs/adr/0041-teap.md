# ADR 0041: TEAP

Status: Accepted (2026-11-10). Phase 5, work package 5.17 ([plans/phase-5-auth.md](../plans/phase-5-auth.md)).

## Context
TEAP (RFC 7170, updated by RFC 9930) is the tunnel method that follows PEAP. Windows 10/11 ship it, and it can
authenticate a machine and a user in one tunnel ("chaining"): typically the computer with its certificate, then the
person with a password. Its inner results are bound to the tunnel by a Crypto-Binding TLV, as in PEAP's
crypto-binding (ADR 0032).

Implementations disagreed on details that RFC 7170 left open (errata, RFC 9930). This one follows what wpa_supplicant
2.12 and hostapd do, and checks the result against them and against an external RADIUS server.

## Decision
- **Method 55, version 1**, on the shared TLS tunnel (`TlsTunnel`).
  - Every message carries version 1 in its flags.
  - The Start has the O flag and an Authority-ID Outer TLV (`auth.eap.teap.authority.id`, default `radiusward`).
  - The peer's Outer TLVs of its first message are kept; both sets enter the Compound MAC.
  - The tunnel authenticates the server only.
- **Phase 2** (TLVs inside TLS):
  - The server asks for the inner identity in an EAP-Payload TLV, then runs the first method of
    `auth.eap.teap.inner`. A Nak picks another listed one.
  - Inner methods: EAP-MSCHAPv2, EAP-GTC, EAP-MD5 (shared with TTLS: `InnerEap`, ADR 0040) and EAP-TLS (a client
    certificate of `auth.eap.tls.ca`, checked as for EAP-TLS outside).
  - With `basic` listed first, a Basic-Password-Auth-Req is sent instead, and the response is checked like PAP. A NAK
    TLV falls back to the listed EAP methods.
  - After each inner method the server sends Intermediate-Result, the Result with the last one, and a Crypto-Binding
    request. The peer must answer with a valid Crypto-Binding response, Intermediate-Result success and, at the end,
    Result success. A failure sends a failed Result first.
- **Keys** (`TeapKeys`):
  - session_key_seed is the TLS exporter `EXPORTER: teap session key seed` (40 bytes, no context) = S-IMCK[0].
  - IMSK is the inner MSK (32 bytes, zero padded), or zeros for methods without keys (GTC, MD5, Basic-Password-Auth).
  - IMCK[j] = TLS-PRF(S-IMCK[j-1], "Inner Methods Compound Keys", IMSK, 60), giving S-IMCK[j] (40) and CMK[j] (20).
  - The final MSK = TLS-PRF(S-IMCK[n], "Session Key Generating Function", 64).
  - TLS-PRF is the TLS 1.2 PRF with the cipher suite's hash (SHA-384 for `_SHA384` suites, else SHA-256), also
    under TLS 1.3.
  - The Compound MAC is an HMAC with the suite's MAC hash, truncated to 20 bytes, over the Crypto-Binding TLV with
    zeroed MACs, the EAP type 55 and both Outer TLV sets.
  - EAP-MSCHAPv2's MSK is the server's send key followed by its receive key: the reverse of PEAP's ISK. That is
    what the peer derives.
  - The server sends the MSK Compound MAC only (flags 2). The peer then binds with its MSK chain, which also makes
    chaining independent of EMSK handling.
- **Chaining**: `auth.eap.teap.identity` (`user`, `machine`, or both in the order asked).
  - Each round sends an Identity-Type TLV with its request, and each inner method's keys extend the previous S-IMCK.
  - The authenticated identity is the user's if there was a user round, else the machine's.
  - Without the setting, any identity is accepted in one round.
- **Resumption**: a resumed TLS session still runs the inner methods. wpa_supplicant's TEAP peer does not offer
  resumption (its ClientHello carries no session), so a shortcut could not be tested.
- **Not covered**: PACs and the provisioning TLVs (PKCS#7/#10, Trusted-Server-Root), Channel-Binding, a client
  certificate in the outer handshake, TLS 1.3-specific key schedules other than the above.

## Test peer
Debian's `eapol_test` (2.10) is built without TEAP. `testing/eapol-test` now builds `eapol_test` from the
wpa_supplicant 2.12 release (checksum pinned) with TEAP and EAP-PWD. All earlier EAP interop tests pass with it.

## Tests
- `TeapKeysTest`: the key hierarchy and the Compound MAC against the values wpa_supplicant 2.12 logged for a
  conversation (suite 0xc02c, SHA-384), including the inner key it derived.
- `TeapTest`: TLV parsing (unknown mandatory TLVs refused, EAP-Payload with TLVs after the packet), configuration
  keys and errors.
- `EapolTestIT`:
  - TEAP with inner EAP-MSCHAPv2, EAP-GTC and EAP-MD5 over TLS 1.2 and 1.3, with wrong passwords;
  - two authentications in a row;
  - Basic-Password-Auth over TLS 1.2 and 1.3;
  - machine (EAP-TLS with its certificate, `host/laptop-1`) then user (EAP-MSCHAPv2) chained in one tunnel, with a
    wrong user password failing the whole.
- `ExternalEapComparisonIT`: TEAP with EAP-MSCHAPv2 inside, right and wrong password, ends the same way on an
  external RADIUS server and on the gateway, with matching keys.
