# ADR 0029: PEAP with EAP-MSCHAPv2

Status: Accepted (2026-11-09). Phase 5, work package 5.8, milestone 3 ([plans/phase-5-auth.md](../plans/phase-5-auth.md)).

## Context
PEAPv0 with EAP-MSCHAPv2 inside is what Windows, Android, iOS and most Wi-Fi clients use with a user name and
password: a TLS tunnel that authenticates the server, and inside it the real identity and an MS-CHAPv2 exchange. The
outer identity is often anonymous; the inner one is the user. With Active Directory the inner check needs Netlogon.

## Decision
- **One TLS base** (`TlsTunnel`) for EAP-TLS, PEAP and TTLS: the RFC 5216 framing and the exporter keys of ADR 0028;
  each method decides what happens after the handshake. PEAP does not ask for a client certificate.
- **Inner exchange** (MS-PEAP): inner EAP messages without their header (type and data), the closing Result TLV with
  it. Identity request → inner identity; MS-CHAPv2 Challenge → Response; the gateway checks it; Success (with the
  authenticator response, so the client verifies the server knew the password) → Success response → Result TLV
  success → EAP-Success. A wrong credential: MS-CHAPv2 Failure `E=691` → Result TLV failure → EAP-Failure.
- **The inner user is the user**: its credential is checked like MS-CHAPv2 outside a tunnel — the store's NT hash,
  cleartext with `auth.store.<name>.mschap`, or a credential verifier (Netlogon for Active Directory). After success
  the whole authorization runs again for the inner identity: its check items, groups, `Simultaneous-Use` and reply
  items. The outer identity needs no store entry.
- **Keys** from the tunnel: label `client EAP encryption` (TLS 1.2), `EXPORTER_EAP_TLS_Key_Material` with type 25
  (TLS 1.3, RFC 9427).
- **Outages**: an inner check that cannot be answered (a verifier down) leaves the request unanswered and keeps the
  conversation and the check; the NAS's retransmission repeats only the check — a TLS record cannot be decrypted
  twice.

## Consequences
- PEAP against Active Directory works through the Netlogon verifier (ADR 0025), without Samba on the gateway.
- Crypto-binding (TLV 12) comes with milestone 5 (verified against `eapol_test`); inner EAP-GTC and EAP-TLS with
  milestone 4b. PEAPv1 is not planned: no current client uses it by default ([ADR 0039](0039-peap-alignment.md)).
- Tested with a JDK TLS client and an inner peer that checks the server's authenticator response; interop with
  `eapol_test` follows in milestone 5.
